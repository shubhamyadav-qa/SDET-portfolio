06 / AUTOMATION ARCHITECTURE

Clear boundaries.
Useful feedback.

A conceptual reference model informed by structures documented in the linked UI and API repositories—not a claim that every project implements every layer.

LAYER 01 / TEST SPECIFICATIONS

Keep intent visible: describe the user or service behavior under test and the result that matters.

WHY SEPARATE LAYERS?

Test intent stays readable, shared code stays reusable, and failures can be traced to the behavior being checked. UI tests exercise browser journeys; API tests validate service contracts. Keep data explicit and tests isolated where the project supports it.

Repository-specific examples: the SauceDemo README describes Page Objects, fixtures, utilities, and GitHub Actions; the API README describes an API client, test data, schema checks, reporting, logging, and a workflow.

HUMAN VALIDATION
  • Compare each scenario with product requirements.
  • Add missing permission, empty-state, and boundary cases.
  • Review locators, assertions, setup, and isolation in any generated script.
  • Reproduce failures and verify the root cause independently.
  • Check generated API cases against actual status and schema contracts.
01 / TEST DESIGN

Turn a requirement into positive, negative, boundary, and edge-case candidates; check each against the stated rules.

02 / SCRIPT DRAFT

Ask for a Playwright or Selenium draft, then review locators, assertions, waits, readability, and test isolation.

03 / API SCENARIOS

Suggest authentication, invalid-payload, status-code, and response-contract cases; verify against the real API contract.

04 / FAILURE ANALYSIS

Use an assistant to interpret error context or suggest refactors; reproduce the issue and verify the root cause independently.

05 / LLM BEHAVIOR
